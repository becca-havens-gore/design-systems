The Constraint That Defines This Story

Most design system work happens inside organizations with existing infrastructure, accumulated decisions, and teams who share context. You inherit something and improve it, govern it, scale it. That's valuable work — and it's the work behind RDS.

AlphaWave was different. I joined as a contract designer with no predecessor, no existing component library, no token structure, no documentation, and no design system thinking established anywhere in the product. The product existed. Patterns did not.

The constraint was also the clarity: every architecture decision was mine to make, and I had to make them fast, under a timeline that didn't allow for second-guessing. This case study is about those decisions — why I made them, what tradeoffs I accepted, and what I built for the team that would carry the system forward after I left.

"The most important design system decisions aren't the ones that look good on day one. They're the ones that still make sense when someone else is maintaining it two years later."

Discovery: Understanding the Inconsistency Before Solving It

Before designing anything, I ran a structured audit of the existing product. The goal wasn't to catalog every visual variation — it was to understand why the inconsistency existed, because different causes require different solutions.

🔍
Product Audit
Screen-by-screen inventory of UI patterns, color usage, spacing, typography, and interactive element variants. Categorized by type of inconsistency: accidental, intentional, and contested.
🗣️
Stakeholder Interviews
Conversations with engineering and product leads about where they felt friction, what they'd built workarounds for, and what they needed from a design system to actually use it.
⚡
Velocity Problem Mapping
Identified the specific patterns that were causing the most repeated decision-making overhead — the ones engineers had to ask about, or make up, every time they built a new screen.

The key finding: most inconsistency was accidental, not intentional. Engineers were making good-faith decisions in the absence of guidance. The product didn't have conflicting design philosophies — it had an absence of shared vocabulary. That diagnosis changed the entire approach to the system I built.

Architecture Decisions: The Choices That Determine Everything Else

A 0-to-1 design system lives or dies by its early architecture decisions. These aren't design decisions in the visual sense — they're structural decisions that determine how easy or hard every subsequent decision will be.

1
Token Structure: Three-Tier Hierarchy
I chose a three-tier token model: primitive tokens (raw values), semantic tokens (purpose-mapped), and component tokens (component-specific overrides). This gave engineering flexibility to consume tokens at the right level of abstraction without creating naming chaos. The naming convention followed a {category}-{variant}-{state} pattern, designed to be readable without documentation.
2
Component Scope: Start With What Blocks Engineering
Rather than building a comprehensive library up front, I scoped the initial component set to the patterns engineers were actively building around or recreating. Buttons, form elements, modals, navigation, data display tables — the patterns with the most duplicate implementations. Everything else was deferred until the core was stable and adopted.
3
Naming Conventions: Optimized for the Maintainer, Not the Builder
I named components and tokens for the person who would maintain them after I left — someone who didn't have my context. Generic, predictable names over clever, contextual ones. Consistent patterns that made extension obvious. The question I asked for every naming decision: "Would someone who joined in 18 months understand this without asking anyone?"
4
Documentation-First Approach
Every component was documented before it was considered done. Usage guidance, anti-patterns, accessibility notes, code snippets, and the rationale for key decisions. Documentation wasn't a deliverable at the end — it was the acceptance criteria for each component. A component without documentation was an incomplete component.

The tradeoff I made consciously

I chose documented simplicity over undocumented sophistication. Some token structures and component APIs could have been more elegant with more time — but an elegant system nobody can extend is worse than a clear system everybody can maintain. Under a contract timeline, clarity wins.

Token Architecture: From Raw Values to Purposeful Language

The token hierarchy was designed to give engineering teams the right level of abstraction at every consumption point, while keeping the Figma-to-code relationship explicit and traceable.

Primitive Raw values with no semantic meaning. Never consumed directly in components. blue-500, space-4, radius-sm
Semantic Purpose-mapped aliases. The primary consumption layer for most engineering work. color-action-primary, space-inset-md
Component Component-specific overrides. Used when a semantic token doesn't capture the exact context. button-bg-primary, input-border-focus

Color tokens covered neutral, brand, feedback (success/warning/error/info), and data visualization scales. Typography tokens captured size, weight, line-height, and letter-spacing as a system — not as ad-hoc values per component. Spacing followed an 8px base grid with named scale steps rather than raw pixel values.

Color — 5 scales Typography — 6 sizes Spacing — 8px grid Border Radius — 4 steps Shadow — 3 elevations Motion — 3 durations + easing

Build Order: Foundations Before Components, Components Before Patterns

The build sequence was deliberate. Jumping to components before foundations are stable creates components that need to be rebuilt when the tokens change. I sequenced the work to avoid that rework.

Phase 1: Foundations

Token system, color palette, type scale, spacing system, grid. These were validated with engineering before any component work began. Getting foundations right first meant components would be stable from the start.

Phase 2: Core Components

Buttons, inputs, selects, checkboxes, radios, modals, toasts, and navigation. Built in priority order based on the velocity audit: highest-friction patterns first. Each component shipped with full state documentation and accessibility specs.

Phase 3: Data Display

Tables, cards, badges, tags, and status indicators — the patterns AlphaWave's product depended on most heavily for its data-forward interface.

Phase 4: Patterns & Templates

Composed patterns (empty states, loading states, error states) and two page templates. These were stretch goals that the timeline didn't fully allow for — they became handoff documentation for the next designer.

Handoff: Designing for the Designer Who Comes Next

A contract system lives or dies by its handoff. I was building for a team that would extend it without my presence — which meant every decision I made had to be self-explanatory, and every gap I couldn't fill had to be clearly marked.

  • Decision rationale documentation: Every significant architectural decision was documented with its rationale, the alternatives considered, and the conditions under which it should be revisited. This prevented future maintainers from accidentally reverting well-reasoned decisions.
  • Extension guides: Step-by-step documentation for the three most common extension tasks — adding a new color to the palette, creating a new component variant, and adding a new component from scratch. Written for someone with no prior context on my process.
  • Anti-pattern catalog: A curated list of patterns to avoid and why, drawn from the original product audit. This was as important as the pattern documentation itself.
  • Open questions log: An explicit list of decisions I had deferred, incomplete patterns, and areas that needed more product definition before they could be systematized. Honesty about what was unfinished was more valuable than pretending the system was complete.
  • Figma file organization: The Figma file was structured as a living document, not a deliverable. Clear page hierarchy, consistent layer naming, component property documentation built into the Figma component descriptions.

"The handoff documentation wasn't a nice-to-have. Under a contract engagement, it was the system. The components are the assets; the documentation is the system."

What I'd Do Differently

Reflection is part of any honest design system story. With more time and resources, I would have changed two things:

  • More validation on the token naming convention before locking it in. I ran the naming past one engineer, which was enough to catch major issues but not enough to surface subtle friction points that only emerge in practice. A broader naming workshop earlier would have saved a few cycles of minor revision.
  • A contribution model from day one. I built the governance documentation toward the end of the engagement, which meant it didn't have time to be validated in use. Starting the contribution model earlier — even as a lightweight draft — would have made the handoff cleaner. The system architecture anticipated contribution; the governance infrastructure was more nascent than I would have liked.

These aren't excuses — they're the specific learnings that shaped how I approached governance at Rapid7, where the Design Forum and FOG framework were built from the start rather than added after.
